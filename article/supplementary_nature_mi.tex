\section{Full Prompt Templates}
\label{sec:s1}

The exact prompt templates used for each of the four experimental tasks are reproduced below. In all templates, \texttt{\{abstract\}} is replaced at runtime with the full text of the target scientific abstract, and \texttt{\{retrieved\_passage\}} is replaced with the domain-relevant context passage for RAG tasks.

\subsection{Task 1: Scientific Summarization}

\begin{lstlisting}[caption={Prompt template for Task 1 (scientific summarization).}]
Summarize the following scientific abstract in exactly
3 sentences. Cover: (1) the main contribution,
(2) the methodology used, and (3) the key quantitative
result.

Abstract: {abstract}

Summary:
\end{lstlisting}

\noindent This is an open-ended generation task. The model must produce three sentences of plain text with no structured markup. The unconstrained output format permits substantial lexical variation across runs.

\subsection{Task 2: Structured Extraction}

\begin{lstlisting}[caption={Prompt template for Task 2 (structured extraction).}]
Extract the following fields from the scientific abstract
below. Return JSON only, no explanation.

Fields: objective, method, key_result, model_or_system,
benchmark

Abstract: {abstract}

JSON:
\end{lstlisting}

\noindent This is a constrained generation task. The model must return a JSON object with exactly five fields. The structured output format reduces but does not eliminate lexical variation.

\subsection{Task 3: Multi-Turn Refinement (3 turns)}

\begin{lstlisting}[caption={Prompt template for Task 3 (multi-turn refinement, 3 turns).}]
Turn 1:
Summarize the following scientific abstract in exactly
3 sentences. Cover: (1) the main contribution,
(2) the methodology used, and (3) the key quantitative
result.

Abstract: {abstract}

Summary:

Turn 2:
Now revise the summary to be more specific about
the quantitative results.

Turn 3:
Add one sentence about the limitations or future work
mentioned.
\end{lstlisting}

\noindent Each turn is submitted as a separate message in the conversation history. For local models, Ollama's \texttt{/api/chat} endpoint is used with an accumulated \texttt{messages} array. For API models, the provider's native chat interface is used with the same message structure. The full conversation state (including all prior turns) is hashed and logged as \texttt{conversation\_history\_hash} in the Run Card.

\subsection{Task 4: RAG Extraction}

\begin{lstlisting}[caption={Prompt template for Task 4 (RAG extraction).}]
Using the context passage below and the scientific
abstract, extract the following fields. Return JSON only.

Context: {retrieved_passage}
Abstract: {abstract}

Fields: objective, method, key_result, model_or_system,
benchmark

JSON:
\end{lstlisting}

\noindent This task augments the structured extraction prompt (Task~2) with a retrieved context passage prepended to the abstract. The context passage is a domain-relevant text segment that provides additional information about the paper's topic. The purpose is to test whether augmenting the prompt with external context affects reproducibility.

\section{Retrieved Contexts for RAG}
\label{sec:s3}

For Task~4 (RAG Extraction), each of the 30 input abstracts is augmented with a domain-relevant context passage prepended to the prompt. These passages serve as simulated retrieval results, providing additional topical information that the model can use when extracting structured fields.

The context passages were curated to satisfy two criteria: (1)~domain relevance to the target abstract's topic (e.g., a passage about attention mechanisms for the Transformer abstract), and (2)~non-overlap with the abstract text itself, to test whether the model integrates external context consistently across repeated runs.

Each context passage is approximately 150--300 words in length and is drawn from survey papers, textbook descriptions, or related work sections of the cited papers. The exact text of every context passage, together with the SHA-256 prompt hash of the augmented input, is recorded verbatim in the \texttt{retrieval\_context} field of each RAG Run Card in the deposited per-run records.

The key finding for RAG tasks is that context augmentation does not substantially improve API reproducibility: on RAG extraction Claude Sonnet~4.5 achieves EMR = 0.000 and Gemini 2.5 Pro EMR = 0.070, comparable to their single-turn extraction reproducibility (RAG was evaluated on the local stacks, Claude, and Gemini; see Methods and the coverage matrix in Section~S10). Local models maintain near-perfect reproducibility regardless of context augmentation (see main text, Table~1).

\section{API Payload Documentation}
\label{sec:s4}

To address potential ``apples-to-oranges'' concerns regarding differences in API request structures across providers, we document the exact JSON payload structures sent to each of the seven inference endpoints. All payloads were constructed deterministically and logged as part of the Run Card. Hyperlinks to the official API references for each provider are listed in Table~\ref{tab:apidocs}.

\paragraph{Comparability across providers.}
Providers expose overlapping but not identical parameter surfaces. What is comparable across stacks is therefore not parameter \emph{equality} but the operational claim that we used the \emph{maximum determinism configuration each provider documents}: temperature zero is universally exposed; the seed parameter is supported by OpenAI (advisory) and Gemini, absent from the Anthropic Messages API surface, and not exposed by DeepSeek's OpenAI-compatible Chat Completions interface or by Perplexity Sonar. Our \texttt{seed\_status} Run Card field records this asymmetry per stack as \texttt{sent}, \texttt{logged-only-not-sent}, or \texttt{not-supported}. \subsection{Ollama (Local Models)}

Single-turn tasks (Tasks 1--2) use \texttt{POST /api/generate}:

\begin{lstlisting}[caption={Ollama generate payload (Tasks 1--2).}]
{
  "model": "llama3:8b",
  "prompt": "<full prompt text>",
  "options": {
    "temperature": 0.0,
    "seed": 42,
    "num_predict": 1024
  },
  "stream": false
}
\end{lstlisting}

\noindent The \texttt{model} field is set to \texttt{llama3:8b}, \texttt{mistral:7b}, or \texttt{gemma2:9b} as appropriate. Multi-turn tasks (Task~3) use \texttt{POST /api/chat} with an accumulated \texttt{messages} array containing alternating \texttt{user} and \texttt{assistant} roles. No system prompt, stop sequences, or post-processing are applied.

\subsection{OpenAI (GPT-4)}

Accessed via the \texttt{openai} Python SDK v1.59.9:

\begin{lstlisting}[caption={OpenAI Chat Completions payload.}]
{
  "model": "gpt-4",
  "messages": [
    {"role": "user", "content": "<prompt>"}
  ],
  "temperature": 0.0,
  "seed": 42,
  "max_tokens": 1024
}
\end{lstlisting}

\noindent No system message, stop sequences, \texttt{top\_p}, \texttt{frequency\_penalty}, or \texttt{presence\_penalty} were set (all defaults). The resolved model version (\texttt{gpt-4-0613}) was extracted from the response object and logged. OpenAI documents that the \texttt{seed} parameter provides ``mostly deterministic'' outputs but does not guarantee bitwise reproducibility.

\subsection{Anthropic (Claude Sonnet 4.5)}

Accessed via \texttt{urllib} (no SDK dependency):

\begin{lstlisting}[caption={Anthropic Messages API payload.}]
{
  "model": "claude-sonnet-4-5-20250929",
  "messages": [
    {"role": "user", "content": "<prompt>"}
  ],
  "temperature": 0.0,
  "max_tokens": 1024
}
\end{lstlisting}

\noindent \textbf{Key difference:} The Anthropic API does not support a \texttt{seed} parameter. The seed value in the Run Card is marked \texttt{seed\_status: "logged-only-not-sent-to-api"}. No system message or stop sequences were used.

\subsection{Google (Gemini 2.5 Pro)}

Accessed via \texttt{urllib} (no SDK dependency) through the Google AI Studio REST API:

\begin{lstlisting}[caption={Google Gemini API payload.}]
{
  "contents": [
    {
      "role": "user",
      "parts": [{"text": "<prompt>"}]
    }
  ],
  "generationConfig": {
    "maxOutputTokens": 8192,
    "temperature": 0.0,
    "seed": 42
  },
  "systemInstruction": {
    "parts": [{"text": "<system>"}]
  }
}
\end{lstlisting}

\noindent \textbf{Key difference:} The \texttt{seed} parameter is supported by the Gemini API and is sent with every request. Gemini 2.5 Pro is a ``thinking'' model: internal reasoning tokens consume the \texttt{maxOutputTokens} budget, hence the higher limit (8,192 vs.\ 1,024 for other models). Multi-turn tasks use the same endpoint with an accumulated \texttt{contents} array alternating \texttt{role: "user"} and \texttt{role: "model"}.

\subsection{DeepSeek (DeepSeek Chat)}

Accessed via the OpenAI-compatible API:

\begin{lstlisting}[caption={DeepSeek Chat API payload.}]
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "user", "content": "<prompt>"}
  ],
  "temperature": 0.0,
  "max_tokens": 1024
}
\end{lstlisting}

\noindent No seed parameter, system message, or stop sequences. DeepSeek Chat achieved the highest API reproducibility (EMR = 0.800 for extraction), suggesting effective internal determinism under greedy decoding.

\subsection{Perplexity (Perplexity Sonar)}

Accessed via the Perplexity API:

\begin{lstlisting}[caption={Perplexity Sonar API payload.}]
{
  "model": "sonar",
  "messages": [
    {"role": "user", "content": "<prompt>"}
  ],
  "temperature": 0.0,
  "max_tokens": 1024
}
\end{lstlisting}

\noindent Perplexity Sonar is an online model with real-time search augmentation. No seed parameter or system message. The search-augmented nature introduces an additional source of variability: retrieved web content may differ across requests, contributing to the lowest observed reproducibility (EMR = 0.010--0.100).

\subsection{Together AI (LLaMA 3 8B)}

Accessed via the Together AI OpenAI-compatible API:

\begin{lstlisting}[caption={Together AI API payload.}]
{
  "model": "meta-llama/Meta-Llama-3-8B-Instruct",
  "messages": [
    {"role": "user", "content": "<prompt>"}
  ],
  "temperature": 0.0,
  "seed": 42,
  "max_tokens": 1024
}
\end{lstlisting}

\noindent Together AI serves the same open-weight LLaMA~3 8B model used locally, enabling a quasi-isolation probe: differences in EMR between local and cloud-served deployments of the same weights can be attributed to infrastructure effects (tensor parallelism, dynamic batching) rather than model architecture or training differences.

\subsection{Key Symmetry Points}

Across all nine model deployments: (1)~identical prompt text (verified by \texttt{prompt\_hash}); (2)~identical temperature ($t = 0.0$); (3)~identical maximum token limit (1,024; 8,192 for Gemini 2.5 Pro to accommodate thinking tokens); (4)~no system messages for single-turn tasks; (5)~no stop sequences; (6)~no post-processing or text normalisation of outputs.

\section{Protocol Minimality -- Ablation Study}
\label{sec:s6}

To substantiate the protocol's minimality claim, we systematically removed each field group from the Run Card schema and assessed which audit questions became unanswerable. The analysis was conducted over 1,864 run records.

\subsection{Field Groups and Audit Questions}

We decomposed the Run Card into eight field groups:

\begin{enumerate}[noitemsep]
    \item \textbf{Identification}: \texttt{run\_id}, \texttt{task\_category}, \texttt{task\_id}, \texttt{interaction\_regime}
    \item \textbf{Model Context}: \texttt{model\_name}, \texttt{model\_version}, \texttt{model\_source}, \texttt{weights\_hash}
    \item \textbf{Parameters}: \texttt{inference\_params}, \texttt{params\_hash}
    \item \textbf{Input/Output}: \texttt{prompt\_text}, \texttt{input\_text}, \texttt{input\_hash}, \texttt{output\_text}, \texttt{output\_hash}, \texttt{output\_metrics}
    \item \textbf{Hashing}: \texttt{prompt\_hash}, \texttt{input\_hash}, \texttt{output\_hash}, \texttt{params\_hash}, \texttt{environment\_hash}
    \item \textbf{Environment}: \texttt{environment}, \texttt{environment\_hash}, \texttt{code\_commit}
    \item \textbf{Timing}: \texttt{timestamp\_start}, \texttt{timestamp\_end}, \texttt{execution\_duration\_ms}, \texttt{logging\_overhead\_ms}
    \item \textbf{Overhead}: \texttt{logging\_overhead\_ms}, \texttt{storage\_kb}
\end{enumerate}

We defined 10 audit questions that a reproducibility-oriented researcher might ask:

\begin{enumerate}[noitemsep]
    \item[Q1.] Can we verify the exact prompt used?
    \item[Q2.] Can we verify the model identity?
    \item[Q3.] Can we verify the generation parameters?
    \item[Q4.] Can we detect output tampering?
    \item[Q5.] Can we verify the execution environment?
    \item[Q6.] Can we reproduce the exact timing?
    \item[Q7.] Can we assess protocol overhead?
    \item[Q8.] Can we trace full provenance?
    \item[Q9.] Can we verify input integrity?
    \item[Q10.] Can we compare outputs across runs?
\end{enumerate}

\section{Chat-Format Control Experiment}
\label{sec:s7}

To assess whether the prompt-format difference between completion-style and chat-style API calls contributes to the observed reproducibility gap between local and API models, we conducted a control experiment running LLaMA~3 8B through two different Ollama endpoints.

\subsection{Design}

\begin{itemize}[noitemsep]
    \item \textbf{Completion format}: \texttt{POST /api/generate} (raw prompt string)
    \item \textbf{Chat format}: \texttt{POST /api/chat} (structured messages with \texttt{role: "user"})
    \item \textbf{Scale}: 10 abstracts $\times$ 2 tasks (summarization, extraction) $\times$ 2 conditions (C1 fixed seed, C2 variable seed) $\times$ 5 repetitions = 200 runs per format, 400 runs total
    \item \textbf{Decoding}: Greedy ($t = 0$, seed = 42 for C1)
\end{itemize}

\subsection{Interpretation}

The chat-format control provides evidence that prompt formatting is \textbf{not} a source of the reproducibility gap between local and API models. The identical metrics across completion and chat formats indicate that the local model produces the same outputs regardless of whether the prompt is presented as a raw string or as a structured chat message. This result supports the interpretation that the local--API gap is driven by infrastructure-level factors (tensor parallelism, dynamic batching, mixed-precision non-determinism) rather than by differences in prompt formatting conventions.

\section{Statistical Test Results}
\label{sec:s9}

\textit{\textbf{Section at a glance.} Of 68 pre-registered pairwise tests (Fisher's exact, Mann--Whitney $U$, Brunner--Munzel, plus paired follow-ups), \textbf{51 remain significant after Holm--Bonferroni control at $\alpha=0.05$}. Cliff's $\delta$ effect sizes for the local--API contrasts fall in the range \textbf{0.784--0.896 (large to very large, Romano--Vargha--Delaney bands)}, indicating that the EMR gap is not a borderline effect but a categorical separation between the two stack classes. The remainder of this section reports the procedure, the per-comparison results, and the effect-size table that supports this summary.}

\subsection{Methodology}

We applied the Holm--Bonferroni sequential rejection procedure to control the family-wise error rate at $\alpha = 0.05$ across all pairwise comparisons. The test battery comprised 68 individual tests:

\begin{itemize}[noitemsep]
    \item 24 Fisher's exact tests (3 local models $\times$ 4 API models $\times$ 2 tasks): testing whether the proportion of abstracts with perfect reproducibility (EMR = 1.0) differs between local and API models.
    \item 24 Mann--Whitney $U$ tests (same pairings): testing whether per-abstract EMR distributions differ between local and API models.
    \item 18 Wilcoxon signed-rank tests (3 local $\times$ 4 API $\times$ 2 tasks, where paired data available on shared abstracts): testing within-abstract EMR differences.
    \item 2 aggregate Mann--Whitney $U$ tests (all local vs.\ all API, per task): testing the overall local--API gap.
\end{itemize}

\subsection{Holm--Bonferroni Procedure}

The Holm--Bonferroni method orders all $m = 68$ $p$-values from smallest to largest and rejects hypothesis $H_{(k)}$ if $p_{(k)} \leq \alpha / (m - k + 1)$ for all $k' \leq k$. This provides strong control of the family-wise error rate without assuming independence among tests.

\paragraph{Scope of the FWER family.}\label{par:fwer-scope}
The 68-test family corresponds to the pre-specified comparisons on Tasks~1--2 (extraction and summarisation). The code, mathematics, and cross-domain results (HumanEval, GSM8K, PubMed PM\textsubscript{2.5}, and the multi-turn extension to gpt-4o and DeepSeek) are \emph{not} part of this pre-specified Holm--Bonferroni family, which was fixed before those batches were collected. We therefore report them descriptively---as per-stack effect sizes (Cliff's $\delta$) and EMR with 95\% bootstrap confidence intervals (main Table~4)---rather than as confirmatory hypothesis tests, and we phrase the corresponding claims accordingly (the local--API gap \emph{persists}, and on the worst-case API stacks widens, on these tasks). Readers wishing a unified multiplicity correction across the full design can apply a Benjamini--Hochberg false-discovery-rate procedure to the per-stack per-task EMR contrasts in Table~4.

\paragraph{Bootstrap behaviour at the EMR boundary.}\label{par:bootstrap-boundary}
The percentile bootstrap was selected for consistency across all analyses, but it is known to produce degenerate intervals when the empirical estimate sits at the boundary of the EMR support (0 or 1). For groups with EMR${=}$1.000 the percentile CI collapses to [1.00,\,1.00]; for groups with EMR${=}$0.000 it collapses to [0.00,\,0.00]. These ``zero-width'' intervals understate uncertainty by design and are reported as such in the tables. Bias-corrected and accelerated (BCa) intervals would marginally widen the boundary CIs but do not change any of the qualitative conclusions in this paper.

\subsection{Summary Results}

Of the 68 tests, \textbf{51 were rejected} (significant) and 17 were not rejected after correction:

\begin{itemize}[noitemsep]
    \item All 24 Fisher's exact tests involving LLaMA~3 8B, Gemma~2 9B, and Mistral~7B versus GPT-4, Claude, and Perplexity were significant.
    \item All aggregate local-vs.-API tests were significant ($p_{\text{adj}} < 10^{-9}$).
    \item The 17 non-rejected tests primarily involved comparisons with DeepSeek Chat, which has the highest API reproducibility (EMR = 0.800 for extraction), making the gap with some local models non-significant at the corrected threshold.
\end{itemize}

\section{LLM-as-Judge Triangulation Protocol}\label{sec:s12}

\textit{\textbf{Section at a glance.} A blinded \textbf{two-judge LLM-as-judge protocol} (Claude Opus~4.7 from Anthropic and gpt-4o from OpenAI---two distinct training families) classified \textbf{30 newly sampled disagreement cases} against three pre-registered criteria (direction, magnitude $\pm$20\,\%, CI overlap). \textbf{Both judges classify the majority as truly contradictory}: Claude 22/30 (Wilson 95\,\% CI 56--86\,\%); gpt-4o 27/30 (74--97\,\%). Inter-judge \textbf{Cohen's $\kappa = 0.29$ (fair agreement, Landis--Koch)}. Both judges' lower bounds exclude a pure-cosmetic interpretation under BERTScore~F1~$>$~0.97 on the same outputs, and the convergence of two independent provider families addresses the residual ``LLM-on-LLM'' concern more directly than a single-judge design would. \textbf{The in-paper protocol is self-sufficient to support the truly-contradictory claim}; the companion paper is cited only as larger-corpus context.}

This section documents the in-paper triangulation of the applied PM\textsubscript{2.5} divergence claim. The validation is layered with the companion paper (Rover \& de Souza Tadano, 2026, OSF: \url{https://doi.org/10.17605/OSF.IO/VR934}) to preserve that paper's contributions while providing self-contained evidence within the present manuscript.

\subsection{Sampling design}

We sampled 30 disagreement cases from the companion-paper extraction corpus (\texttt{extraction\_long.json}, 21{,}799 extractions), distinct from the 23 study-level effect estimates analysed in the companion paper. Cases were drawn in two waves: an initial 10 cases (seed = 42) followed by 20 additional cases (seed = 4242) to extend the sample for inter-judge analysis. Cases were drawn from the three cloud stacks where disagreement is highest (Claude Sonnet 4.5, Gemini 2.5 Pro, GPT-4.1; per the companion paper's pairwise-disagreement analysis). Stratification was applied across both waves to balance across stack and across kind of disagreement (direction, magnitude, CI overlap, mixed).

A disagreement case is a pair of runs (within the same stack, the same input abstract, and the same estimate index) whose effect estimate, CI bounds, or sign differs beyond pre-registered thresholds. Final composition: 18 Claude Sonnet 4.5 cases and 12 GPT-4.1 cases (Gemini had insufficient strictly disagreeing pairs under our thresholds in either wave), distributed across direction, magnitude, CI overlap, and mixed strata.

\subsection{Judges and prompt}

Two independent LLM judges from distinct provider families were used: Claude Opus 4.7 (model identifier \texttt{claude-opus-4-7}, Anthropic Messages API) and gpt-4o (\texttt{gpt-4o-2024-11-20}, OpenAI Chat Completions API). Each judge received the same system prompt instructing pre-registered evaluation along three criteria:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Direction.} Do both extractions report the same direction of effect? (positive, null, negative)
    \item \textbf{Magnitude.} Do the effect estimates agree within $\pm 20\%$ relative to their average?
    \item \textbf{CI overlap.} If both 95\% CIs are reported, do they share any range?
\end{enumerate}

Each judge issues one verdict per case from \{\texttt{truly\_contradictory}, \texttt{semantically\_equivalent}, \texttt{ambiguous}\} plus a brief rationale. The two extractions are presented as ``Extraction X'' and ``Extraction Y'' in deterministically randomised order (per-case seed derived from SHA-256 hash of the case identifier) to prevent positional bias. Each judge is blind to which stack produced which extraction and to the other judge's verdict.

The verbatim system prompt given to both judges was:

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize,numbers=none]
You are an expert in environmental epidemiology evaluating whether two
extractions of effect-estimate data from the same scientific abstract are
*materially the same* or *materially different* for evidence synthesis.

You must judge against THREE pre-registered criteria:
(a) DIRECTION: do both extractions report the same direction of effect
    (positive / null / negative)?
    - Ratio measures (RR, OR, HR): "positive" >1.0, "negative" <1.0,
      "null" ~1.0 with CI overlapping 1.0.
    - Risk differences: "positive" >0, "negative" <0.
(b) MAGNITUDE: do the effect estimates agree within +/- 20% relative to
    their average?
(c) CI OVERLAP: if both 95% CIs are reported, do they share any range?

Then issue ONE of three verdicts:
  - truly_contradictory: at least one of (a), (b), (c) materially fails
  - semantically_equivalent: all three criteria hold (textual diffs only)
  - ambiguous: data missing or judgment uncertain

Return STRICTLY as JSON:
{ "criterion_a_direction": "same"|"different"|"ambiguous",
  "criterion_b_magnitude":  "same"|"different"|"ambiguous",
  "criterion_c_ci_overlap": "overlap"|"disjoint"|"ambiguous",
  "verdict": "truly_contradictory"|"semantically_equivalent"|"ambiguous",
  "rationale": "<one or two sentences>" }
Do NOT add commentary outside the JSON.
\end{lstlisting}

The per-case user message supplies the source abstract and the two extractions in randomised positions (``EXTRACTION X'' / ``EXTRACTION Y'') and closes with ``Apply the three pre-registered criteria and return your verdict as JSON only.''

\textbf{Decoding parameters.} The two judges were called under their respective maximally-deterministic configurations, which differ by provider surface: Claude Opus~4.7 with \texttt{max\_tokens}~=~600 and no \texttt{temperature} parameter (the Opus~4.7 surface does not accept it), and gpt-4o with \texttt{max\_tokens}~=~600, \texttt{temperature}~=~0, and \texttt{seed}~=~42. Each verdict is single-shot; the categorical verdict is read directly from the model's \texttt{verdict} field (no post-hoc re-mapping), and responses that failed JSON parsing were re-requested once. The judges are themselves API-served models subject to the non-determinism this paper documents; the cross-provider two-judge design and the agreement between two independently-sampled provider families mitigate, but do not eliminate, this reflexivity, which we flag as an inherent limitation of LLM-as-judge validation.

\subsection{Cost and provenance}

Total cost across 30 cases $\times$ 2 judges = 60 LLM-as-judge calls: USD~0.28 (Claude Opus 4.7 on Anthropic API; mean 929 input + 137 output tokens per case at \$15/MTok input, \$75/MTok output) + USD~1.02 (gpt-4o on OpenAI API; mean 1{,}100 input + 145 output tokens per case at \$2.50/MTok input, \$10/MTok output) = USD~1.30. Per-case judge records (input prompt SHA-256, model identifier, randomisation seed, raw response, parsed verdict, token counts, cost) are deposited as PROV-style JSON in the project repository, one record per case, together with the two-judge aggregate file reporting Cohen's $\kappa$.

\subsection{Future work: multi-rater human validation}\label{sec:s12-future-work}

To confirm whether the PM\textsubscript{2.5} divergences are truly contradictory or merely semantically varied, we conducted a cross-provider two-judge LLM-as-judge analysis (Claude Opus 4.7 from Anthropic and gpt-4o from OpenAI). The convergence of two judges from distinct training families directly addresses the standard ``LLM-on-LLM'' bias concern that a single-judge design would expose.

A dedicated methodological extension applying multi-rater human validation against a domain-expert silver standard on a larger sample is in preparation as a follow-up paper. That paper will (i) increase the sample to $\geq$50 cases, (ii) recruit two or more external epidemiologists not on the present author list, (iii) compute Fleiss' $\kappa$ across humans, LLM judges, and the existing silver standards, and (iv) test whether the human-rater verdict distribution differs from the LLM-judge verdict distribution under formal hypothesis testing. The infrastructure for that work---blinded case packages, rating forms, and the $\kappa$ analysis pipeline---is already deposited in the project repository (\texttt{human\_validation/}) and is reusable by independent groups.

\section{Per-field reproducibility on structured extraction}\label{sec:s10b}

\textit{\textbf{Section at a glance.} Computing every reproducibility metric \emph{per JSON output field} reveals an unexpected stronger argument: \textbf{paired Cohen's $d = +1.41$ EMR gap} between conclusion-relevant fields ($\overline{\text{EMR}} = 0.455$) and metadata fields ($\overline{\text{EMR}} = 0.684$)---a very large effect. \textbf{BERTScore~F1 is structurally saturated} across both groups (0.978 vs 0.979, paired $d = -0.10$, effectively null). The most striking single-stack case is Gemini~2.5~Pro RAG on \texttt{key\_result}: EMR~$=$~0.10 (the field changes 90\,\% of the time) while BERTScore~F1 remains 0.969. \textbf{BERTScore alone is structurally unable to discriminate substantive payload divergence from cosmetic textual variation} on extracted-JSON fields of moderate length; the three-level reproducibility framework (bitwise $\to$ structural $\to$ semantic) we propose is necessary.}

This section quantifies how the local--API reproducibility gap distributes across the five fields returned by the structured-extraction task (Task~2): \emph{objective}, \emph{method}, and \emph{key\_result} (conclusion-relevant payload) versus \emph{model\_or\_system} and \emph{benchmark} (metadata identifiers). It resolves the apparent tension between high aggregate BERTScore and the assertion that divergences affect substantive content.

\subsection{Protocol}

For every (stack, abstract) group with at least two valid extractions, we computed pairwise within-group metrics on each field separately---Exact Match Rate (EMR), Normalised Edit Distance (NED), ROUGE-L F1, and BERTScore F1 (\texttt{roberta-large}, no baseline rescaling). Pairs in which at least one repetition omitted the field were skipped (rather than penalised), so the metric isolates the question ``when both repetitions emit the field, how similar are they?''. Per-stack point estimates are mean-of-pair-means; 95\% percentile bootstrap CIs use 10{,}000 resamples (seed${=}$42), matching the methodology of Section~\ref{sec:s9}.

\subsection{Aggregate result}

Across the six API stacks where outputs actually diverge (i.e., excluding the three local stacks with EMR${=}$1.000 on most fields), the gap between conclusion-relevant fields and metadata fields is large on EMR but absent on BERTScore. The API-only aggregate (from the per-field BERTScore results file in the repository):

\begin{itemize}[leftmargin=*]
  \item Conclusion-relevant fields ($\overline{\text{EMR}}{=}0.455$) versus metadata fields ($\overline{\text{EMR}}{=}0.684$). Paired Cohen's $d{=}+1.41$ (very large effect).
  \item BERTScore F1: $\overline{\text{conclusion}}{=}0.978$ vs $\overline{\text{metadata}}{=}0.979$. Paired Cohen's $d{=}-0.10$ (effectively null).
  \item NED and ROUGE-L F1 show small effects ($|d|{<}0.5$) in the same direction as EMR.
\end{itemize}

\noindent The single most striking single-stack illustration is \textbf{Gemini~2.5 Pro on RAG extraction, \texttt{key\_result} field}: EMR${=}$0.10 (the field changes content in 90\% of pairs) while BERTScore~F1 remains 0.969 on the same pairs.

\subsection{Per-stack per-field table}

Table~\ref{tab:per_field_metrics} (auto-generated from the same JSON file) reports per-stack per-field EMR, NED, ROUGE-L F1, and BERTScore F1 with 95\% bootstrap CIs across 13 stacks and 5 fields. The pattern from the aggregate above is visible at the stack level: API stacks where outputs diverge show conclusion-field EMR drops of 0.15--0.25 relative to metadata fields, while BERTScore is flat to within $\pm 0.02$ across field types for every stack.

\subsection{Interpretation}

These results resolve the apparent contradiction between ``textual not semantic'' (BERTScore F1 saturated---$>$0.97 on whole outputs and $>$0.94 on every individual field) and ``affects substantive content'' (the 67\% \texttt{key\_result} divergence rate reported in Extended Data Table~7). The resolution is that \emph{BERTScore is structurally unable to discriminate the substantive payload divergence concentrated in conclusion-relevant fields from the cosmetic textual variation distributed across all fields} when one operates on extracted-JSON fields of moderate length. EMR can; NED partly can. The three-level reproducibility framework (bitwise $\rightarrow$ structural $\rightarrow$ semantic) that the manuscript proposes is therefore not redundant: any single metric, including a state-of-the-art semantic-similarity metric, would mislead on this corpus and at this granularity.

\vspace{0.5em}
\par\noindent\textbf{Hypothesis verdict.} A natural hypothesis is that BERTScore~F1 would be \emph{lower} on conclusion-relevant fields than on metadata fields. On the API-only aggregate ($n{=}6$ stacks), BERTScore~F1 is 0.978 for conclusion-relevant fields and 0.979 for metadata fields ($\Delta{=}+0.0010$, paired benchmark vs.\ key\_result Cohen's $d{=}-0.10$); the metric is therefore saturated on both groups and \emph{cannot} discriminate between them, which is itself an important finding---BERTScore obscures rather than reveals the substantive divergence. EMR, by contrast, shows a sharp separation: 0.455 (conclusion-relevant) vs.\ 0.684 (metadata), $\Delta{=}+0.229$, paired Cohen's $d{=}+1.41$. This validates the manuscript's claim that the divergence concentrates on the substantive payload (\emph{objective}, \emph{method}, \emph{key\_result}) and supports adopting a multi-metric three-level framework rather than relying on aggregate BERTScore alone.
